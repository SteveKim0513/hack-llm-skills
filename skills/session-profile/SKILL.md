# session-profile: AI 활용 행동 프로필과 이해 확인

두 모드로 이루어져 있고, **기본은 A → B 순서로 모두 실행한다.** 어느 쪽을 할지 사용자에게 고르게 하지 않는다. 사용자가 "프로필만", "퀴즈만"처럼 하나를 콕 집어 요청했을 때만 그것만 한다.
- **모드 A, 행동 프로필:** 로그에서 사용자가 한 행동의 증거를 센다.
- **모드 B, 이해 확인 퀴즈:** 로그로 알 수 없는 "이해"를 사용자에게 직접 묻는다.

### 전체 순서
1. **범위를 한 번에 정한다.** 볼 도구와 모드 A의 기간, 모드 B의 기간(기본 최근 2주)을 한 질문으로 묻고, 답이 없으면 기본값으로 간다. 모드 B에서 다시 묻지 않는다.
2. **모드 A** 2~7단계(8단계 유형 나누기는 요청할 때만).
3. **모드 B** B2~B9단계. 모드 A가 끝나면 묻지 않고 이어서 시작하고, 시작할 때 한 줄로 알린다. 예: "프로필 끝. 이어서 최근 2주 기록으로 이해 확인 퀴즈를 만들게요."
4. **종합:** 마지막에 한 화면으로 묶는다. 모드 A의 프로필 핵심(행동별 세션 비율과 10발화당 장면 수), 모드 B의 문항별 결과, 그리고 **생각과 실제가 다른 곳** 목록. 같은 프로젝트에서 A와 B가 서로 다른 그림을 보이면(예: 검증 장면은 많은데 퀴즈에서 실제 동작을 다르게 알고 있음) 그 점을 짚는다. 원인을 단정하지 않는다.

모드 A의 사용자 확인(4단계)과 모드 B의 퀴즈 풀이(B6)는 사용자의 시간이 드는 단계다. 사용자가 중간에 멈추면 그때까지의 결과로 종합하고, 남은 단계는 이름만 알린다.

한 사용자의 표본 20건을 직접 확인한 결과, 로그만으로는 "세부 없이 받아들였다", "이해하지 못했다"를 판정할 수 없었다. 승인 한마디("네", "이어서")에는 이해의 흔적이 없고, 있더라도 로그 밖에 있기 때문이다. 그래서 모드 A는 **있었던 행동만 센다.** 없었다고 낮은 수준으로 추정하지 않는다. 이해 여부가 궁금하면 모드 B로 직접 묻는다.
작업 중에 기준이 비어 있는지 묻는 건 `criteria-gap`의 일이다. 이 스킬은 그것을 대신하지 않는다.
선행 연구와 지표는 `references/prior-work.md`에 정리해 두었다. 가장 가까운 선례는 Anthropic의 AI Fluency Index(대화마다 행동 유무를 분류)이고, 로그 기반으로 "수준"이나 "유형"을 검증한 연구는 찾지 못했다.

## 전제
- 세션 기록의 위치와 형식은 도구마다 다르다. 읽기 전에 `references/claude.md`, `references/codex.md`를 본다.
- **결과 파일에는 대화 원문이 들어간다.** 기본 저장 위치는 `~/.criteria/audit/`이고 공개 저장소 안에는 저장하지 않는다. 사용자가 저장소 안을 지정하면 먼저 경고한다.
- 분류가 맞는지는 사용자가 판정한다. 사용자 대신 확정하지 않는다.
- 본인 점검용이다. 다른 사람을 평가하는 데 쓰면 타당성을 보장할 수 없다.

## 네 가지 행동 (모두 "한 일"의 증거)
- **검증:** AI의 오류나 불일치를 짚음, 주장에 근거를 요구, 확인·테스트·재현을 지시, 도메인 지식으로 바로잡음. 승인 앞뒤에서 내용·한계·예외를 묻는 질문도 이해를 확인한 것으로 본다.
- **구조:** 요청을 목표·조건·산출물·순서·성공 기준으로 나눠 줌, 구체적인 제약과 수치를 더함.
- **방향 주도:** 방향을 정하거나 바꾸거나 거절함, AI의 제안을 고침, 이유를 들어 선택함.
- **메타인지:** 자기가 모르는 영역이나 정해지지 않은 기준을 인지하고 탐색·학습에 쓰거나, 자신의 이전 결정을 다시 점검함.

Index 행동과의 대응표는 `references/prior-work.md`에 있다(이 스킬 작성자의 해석). 메타인지에는 대응하는 Index 행동이 없다.

## 세지 않는 것
- **진행 신호:** "이어서", "네", "좋아", "진행해" 같은 짧은 말. 행동이 아니라 작업이 이어지는 것이다.
- **판정 불가:** 맥락에 이해나 의도의 흔적이 없는 승인. 낮은 이해로 세지 않고 "분류 제외 N건"으로만 표시한다.
- "이제 뭐할까?"는 이슈를 닫고 다음 문제를 찾으려는 말일 수 있다. AI 제안을 따른 것으로 세지 않는다.
이 기본값은 한 사용자의 표본에서 나왔다. 4단계에서 본인 표본으로 맞는지 확인한다.

## 모드 A: 행동 프로필

### 1. 범위
"전체 순서" 1번에서 함께 정한다. 프로필만 따로 요청받았을 때는 아래 둘만 묻고 나머지는 기본값으로 진행한다.
- 어느 도구의 기록을 볼지 (기본: 찾은 모두)
- 기간 (기본: 제한 없음. 비교용 리포트면 기간 길이를 맞춘다)

### 2. 추출
`scripts/extract_sessions.py`가 사람이 쓴 발화와 AI 응답만 뽑는다. 서브에이전트 기록, 도구가 끼워 넣은 알림, 다른 도구에서 가져온 사본, 같은 세션 id의 중복 파일, 사용자 발화가 너무 적은 세션이 빠진다.
```bash
python3 scripts/extract_sessions.py --stats-only
python3 scripts/extract_sessions.py --sample 25 --out ~/.criteria/audit/sample.jsonl
```
- 먼저 `--stats-only`로 남은 세션 수와 프로젝트 분포를 한 줄로 알린다. 한 프로젝트가 대부분이면 그 사실도 알린다.
- **분류 기준을 만드는 단계**는 직접 확인할 수 있는 크기로 작게, 프로젝트·도구가 골고루 섞이게 뽑는다(`--sample`). 측정 단계는 표본 없이 전체 또는 기간으로 자른다.
- 추출된 AI 응답은 길면 잘려 있다. 이를 근거로 한 판단에는 "잘림"을 표시한다.

### 3. 행동 찾기
세션 묶음별로 위 네 행동의 장면을 찾는다. 뜻으로 찾는다. 어떤 언어로 쓰였어도 같다. 장면마다 기록한다.
- `quote`: 사용자 발화. **400자 이하면 발화 전체**를 인용한다(한 줄만 자르지 않는다). 더 길면 관련 구절을 400자 이내로. 붙여넣은 내용은 증거로 쓰지 않는다. 인용할 수 없으면 버린다.
- `ai_context`: 직전 AI 발화 요지 한 줄
- `axis`: 네 행동 중 하나, `position`: 시작 / 새 방향 / 응답
- `strength`: 분류에 대한 AI의 확신도(강함: 다르게 읽을 여지가 거의 없음, 보통: 자연스럽지만 다른 해석 가능, 약함). 사용자의 수준이 아니다.
- 세션마다 `task_type`을 한 가지 붙인다(코딩·개발 / 기획·글쓰기 / 분석·조사 / 학습 / 기타 중 주된 것). 과제 유형에 따라 행동이 나오는 정도가 달라서 리포트에서 나눠 본다.
- **행동을 채우려고 하지 않는다.** "네 축을 모두 찾으라"고 지시하면 모든 세션에 모든 행동이 있는 것처럼 나와 세션 비율이 부풀려진다. 증거가 분명한 장면만 기록하고, 없으면 비워 둔다.
- 한 세션에서 상한(예: 15건)에 걸리면 건너뛴 수를 기록한다. 리포트가 상한에 걸린 세션 수를 표시한다.
- 병렬로 나눌 때는 일꾼마다 **자기 출력 파일**을 따로 주고 다른 곳에 쓰지 못하게 한다(공용 작업 폴더를 쓰다 파일이 덮어써질 뻔한 적이 있다). 합친 뒤 인용이 실제 발화의 부분 문자열인지 코드로 검증한다.

### 4. 사용자가 분류 확인하기 (기준 만들기)
표본을 뽑아 `scripts/label_server.py`로 로컬 웹 화면에 띄운다. 127.0.0.1에서만 열리고, 답은 바꿀 때마다 파일에 저장된다.
```bash
python3 scripts/label_server.py --queue ~/.criteria/audit/queue.json --labels ~/.criteria/audit/labels.json
```
- 카드마다 앞 대화 3턴, 발화 전체, AI 분류를 보여 주고 `맞음 / 아님(어느 쪽이 맞는지) / 애매`를 받는다. 이유 한 줄은 선택이다.
- 표본은 네 축이 모두 들어가고 진행 신호처럼 분류 제외 후보가 섞이게 한다. 한꺼번에 많이 묻지 않는다.
- 한 번에 하나씩 대화로 물을 때는 앞 2~3턴을 같이 보여 준다. 한 줄 요지만으로는 판단이 안 되는 경우가 많았다.
- 축별로 `맞음` 비율을 센다. **표본 수를 같이 쓴다.** 수가 적으면 참고용이라고 밝힌다.

### 5. 분류 기준 정리
판정 이유를 모아 이 사용자의 분류 기준을 문장으로 만든다.
- 같은 이유가 **두 번 이상** 나온 것만 기준 후보로 올리고, 한 번 나온 건 사례로 둔다.
- 후보를 보여 주고 사용자가 고친 뒤 확정한다. 확정 전에는 초안으로 `~/.criteria/audit/rubric.md`에 둔다.
- 사용자가 원하면 `criteria` 스킬의 저장 전 점검을 거쳐 기록소에도 저장한다.

### 6. 전체 측정
확정한 기준과 사용자 판정 예시로 나머지 세션을 분류한다. AI의 분류이므로 **일치율**을 같이 낸다.
- 사용자가 확인하지 않은 장면 중 일부를 무작위로 뽑아 확인받고, AI와 사용자가 얼마나 같았는지 센다.
- 일치율이 낮으면 숫자를 쓰지 않고 5단계로 돌아가 기준을 고친다.

### 7. 리포트
`scripts/build_report.py`가 세션 단위 리포트를 만든다.
```bash
python3 scripts/build_report.py --sessions ~/.criteria/audit/sample.jsonl --events ~/.criteria/audit/events.json \
  --labels ~/.criteria/audit/labels.json --out ~/.criteria/audit/report-<날짜>.md
```
- **두 지표를 함께 본다.**
  - **세션 비율:** 그 행동이 한 번이라도 나온 세션 / 분석한 세션. 대화 길이, 과제 유형, 프로젝트별로 나눠 보여 준다.
  - **10발화당 장면 수:** 상한에 걸린 세션을 빼고 세션을 합쳐 계산한다(짧은 세션 하나가 비율을 흔들지 않게). 세션별 분포는 발화 10개 이상 세션만 쓴다.
- 장면 수를 그대로 비교하지 않는다. 대화가 길수록 늘어난다.
- 어떤 행동이 85% 이상의 세션에서 나오면 세션 비율의 구분력이 낮다는 경고가 붙는다. 이때는 10발화당 장면 수와 대표 장면 인용(행동마다 2~3개, 발화 전체와 직전 AI 요지)을 중심으로 보여 준다.
- 장면의 40% 이상이 대화 시작이나 새 방향에서 나오는 행동(확인한 표본에서는 구조, 메타인지)은 긴 대화일수록 발화당 비율이 낮아진다. 이런 행동은 "응답 중 장면만" 비율로 본다. 길이별 표에서 값이 크게 다르면 길이가 비슷한 세션끼리만 비교한다.
- 이 지표들을 고른 근거와 한계는 `references/validation-notes.md`에 있다.
- 분류 제외 건수, 사용자 확인 건수와 축별 `맞음` 비율(표본 수 포함), 상한에 걸린 세션 수가 함께 나온다.
- 이전 리포트가 있으면 같은 기준·같은 기간 길이일 때만 비교한다. 다르면 비교하지 않고 이유를 쓴다.
- 대화에는 결론 한 줄 뒤에 위 표의 핵심만 보여 준다.

### 8. 유형 나누기 (선택)
사람 간 유형이 필요할 때만 한다. **한 사람의 기록으로는 그 사람 안의 세션 간 차이만 보이고, 사람 간 유형은 만들 수 없다.**
- 특징은 네 행동의 세션 비율, 사용자 발화 수, 발화 길이처럼 로그에서 셀 수 있는 것으로 한다.
- 군집을 먼저 보고, 이름은 사용자와 함께 붙인다. 이름에 상하 등급을 붙이지 않는다.
- 외부 기준으로 맞는지 확인한다. 예: 같은 사람들이 `references/prior-work.md`의 검증된 설문(Critical Thinking in AI Use Scale 등)에 답해서 군집과 맞는지 본다. 확인 전에는 "유형"이라 부르지 않고 "경향"이라 쓴다.

## 모드 B: 이해 확인 퀴즈
AI가 결정이 걸린 긴 답변을 냈는데 사용자가 "진행해"처럼 짧게 승인하고 넘어간 지점을 골라, **그 결정으로 생긴 지금의 환경**을 알고 있는지 서술형으로 묻는다. 가장 쓸모 있는 결과는 점수가 아니라 **"내가 아는 것과 실제 시스템이 다른 곳"** 이다. 문항 규칙과 일꾼 지시문은 `references/quiz.md`에 있다.

이 모드는 서로 독립된 에이전트(서브에이전트) 여럿이 필요하다. 문항을 만든 쪽이 검증까지 하면 검증이 무의미해진다. 그런 기능이 없는 환경이면 퀴즈를 낼 수는 있지만 "검증 안 됨"이라고 밝힌다.

### B1. 범위
"전체 순서" 1번에서 정한 기간(기본 최근 2주)과 도구를 그대로 쓴다. 퀴즈만 따로 요청받았을 때만 여기서 묻는다. 지금 진행 중인 대화는 뺀다. 기억이 너무 생생해 시험이 되지 않는다.

### B2. 지점 고르기
```bash
python3 scripts/extract_sessions.py --since <날짜> --max-chars 3000 --out ~/.criteria/audit/recent.jsonl
python3 scripts/pick_points.py --sessions ~/.criteria/audit/recent.jsonl --out ~/.criteria/audit/quiz/packets.json \
  --exclude-session <지금 세션 id>
```
지금 세션 id를 모르면 `--exclude-session` 없이 돌리고, 나온 패킷 중 지금 대화의 것을 뺀다.
짧은 승인(25자 이하, 질문 아님)이고, 직전 AI 답변이 길며(600자 이상) 결정 신호(제안, 선택지, "할까요?")가 두 개 이상이고, 그 뒤에 이어진 대화가 있는 지점이다. 프로젝트를 돌아가며 세션당 하나씩 고른다.

### B3. 문항 쓰기
패킷마다 서술형 문항을 하나(드물게 둘) 만든다. 일반 원리가 아니라 그 프로젝트에서 정한 결과, 누가 무엇을 하는지, 남겨 둔 것, 포기한 것을 묻는다. 참/거짓이나 객관식은 쓰지 않는다. 결정의 승인이 아니거나 맥락 문항이 안 나오는 패킷은 건너뛴다.

### B4. 정답 기준을 지금 기준으로 고치기
문항마다 이후 세션과 저장소(읽기만)를 확인해 원래 시점 이후의 변화를 찾고, 정답 기준을 지금 상태로 맞춘다. **이 단계를 빼면 이후 변화까지 아는 사람이 오히려 틀린다.** 시험에서 5문항 중 2문항이 이렇게 잘못 채점됐다.

### B5. 문항 검증
대화를 읽은 일꾼과 대화를 보지 않은 일꾼이 각자 답하고, 출처를 모르는 채점 일꾼이 둘을 채점한다. **대화를 읽은 답은 맞음, 대화를 보지 않은 답은 틀림인 문항만** 남긴다.
```bash
python3 scripts/quiz_check.py prepare --items items.json --packets packets.json --out blind/
python3 scripts/quiz_check.py grading --items items.json --context blind/context-answers.json \
  --nocontext blind/nocontext-answers.json --out blind/grading.json --map map.json   # 지도는 다른 폴더에
python3 scripts/quiz_check.py select --items items.json --grades blind/grades.json --map map.json \
  --packets packets.json --out quiz.json
```
대화를 보지 않는 일꾼은 프로젝트 지시 파일이 자동으로 읽히지 않는 곳에서 돌린다. 통과 문항이 적으면 억지로 채우지 않는다.

### B6. 풀기
```bash
python3 scripts/quiz_server.py --items quiz.json --answers answers.json --grades grades.json
```
127.0.0.1에서만 열린다. 사용자는 한두 문장으로 답하고 확신도를 고르거나, "모르겠음", "맡긴 부분이라 몰라도 됨"을 고른다. 정답 기준은 제출하고 채점이 끝난 뒤에만 나온다.

### B7. 채점과 이의
채점 일꾼이 정답 기준으로 채점해 `grades.json`을 채운다. 사용자가 "이의"를 고르면 이후 세션과 저장소로 그 답을 다시 사실 확인하고, "지금 사실과 맞음 / 그때 기준으로만 맞음 / 부분 / 틀림 / 확인 불가"와 근거를 붙여 고친다. 원래 채점은 지우지 않고 따로 남긴다.

### B8. 결과
문항마다 이해 / 부분 이해 / 확신 오답 / 틀림 / 모름 / 맡김 중 하나를 보여 준다. 몇 문항으로 수준을 매기지 않는다. 대신 **생각과 실제가 다른 곳**을 근거(코드 위치, 커밋, 세션)와 함께 따로 모아 보여 주고, 코드를 고칠지 이해를 고칠지는 사용자가 정하게 한다.

### B9. 정리
패킷과 추출본에는 대화 원문과 비밀 값이 들어 있을 수 있다. 끝나면 지울지 묻는다. 문항, 근거 인용, 출력에는 비밀 값을 옮기지 않는다.

## 한계
- 로그는 "검증을 시작했나"까지만 보여 주고, 과정의 질과 성공 여부는 보여 주지 않는다.
- 머릿속 모니터링과 채팅 밖에서 한 확인은 로그에 없어서 과소 집계된다.
- 자가보고와 실제 행동은 어긋나므로 설문만으로 대신할 수 없고, 로그만으로도 충분하지 않다.
- 분류는 AI의 판단이다. 사용자 확인 건수와 일치율을 항상 같이 쓴다.
- 퀴즈는 비용이 크다. 문항마다 에이전트가 이후 세션과 저장소를 확인해야 한다. 한 번의 시험에서 16개 지점으로 시작해 통과 문항은 7개였다.
- 퀴즈 채점도 AI의 판단이라 틀릴 수 있다. 이의와 재확인 기록을 남기고, 채점이 자주 뒤집히면 문항이나 기준을 고친다.

## 하지 않는 것
- 점수 하나로 "수준"을 매기거나 "N% 이상이면 좋음" 같은 기준선을 제시하지 않는다.
- 행동이 관찰되지 않았다는 이유로 낮은 이해나 낮은 수준을 추정하지 않는다.
- 공백 비율을 재지 않는다. 로그만으로는 판정되지 않았다. 공백은 `criteria-gap`으로 작업 중에 묻는다.
- 인용 없는 장면을 세지 않는다. AI 분류를 사용자 확인처럼 섞어 세지 않는다.
- 표본이 작은데 정확한 숫자처럼 쓰지 않는다.
- 결과 파일과 리포트를 공개 저장소에 넣지 않는다.
- 퀴즈에서 참/거짓, 객관식 이유 보기를 쓰지 않는다. 대화를 보지 않은 AI가 20문항 중 19개, 22문항 중 22개를 맞혔다.
- 저장소를 확인할 때 아무것도 고치거나 실행하지 않는다. 읽기만 한다.
