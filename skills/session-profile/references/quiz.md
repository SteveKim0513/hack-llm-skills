# 이해 확인 퀴즈: 문항 규칙과 일꾼 지시문

SKILL.md의 "모드 B"에서 쓴다. 규칙마다 근거가 된 시험 결과는 `validation-notes.md`에 있다.

## 문항 규칙
- **일반 지식이 아니라 그 결정으로 생긴 환경을 묻는다.** 결과("지금 구조에서 X하면 어떻게 되나"), 환경(누가 무엇을 하나, 무엇이 자동이고 수동인가, 어디서 도나), 남겨 둔 것(미뤄 둔 일), 포기한 것. "마이그레이션은 앞으로만 간다" 같은 보편 원리는 맥락 없이도 풀린다.
- **서술형으로 묻는다.** 참/거짓이나 객관식 이유 보기는 쓰지 않는다. 보기 중 문장을 일관되게 설명하는 하나가 정답을 알려 준다.
- 예/아니오 질문, 정답의 핵심어가 든 질문, 숫자·파일 이름·함수 이름·문구를 묻는 질문은 쓰지 않는다.
- 상식적인 기본값과 다르게 정한 결정, 또는 여러 합리적인 선택지 중 하나를 고른 결정을 우선한다.
- **정답 기준은 "지금" 기준이어야 한다.** 원래 세션이 끝난 시점에 멈춘 기준은 이후 변화를 아는 사람을 틀리게 만든다. 이후 세션과 저장소로 확인한다.
- 대화에 비밀번호, 키 같은 비밀 값이 있으면 문항, 근거 인용, 출력 어디에도 옮기지 않는다.
- 문항을 못 만들면 억지로 만들지 않고 건너뛴다.

## 문항 형식
```json
{"item_id": "Q<pid>-<n>", "pid": 0, "type": "결과|환경|남김|포기",
 "question": "한두 문장, 자립적인 질문",
 "key_points": ["정답에 들어가야 할 사실 1~3개"],
 "full_credit": "맞음 조건 한 줄", "partial_credit": "부분 조건 한 줄",
 "common_wrong": "상식으로 답하면 나올 답과 그게 틀린 이유",
 "then_state": "원래 세션이 끝난 시점의 상태", "now_state": "지금 상태",
 "later_changes": [{"date": "", "what": "", "source": ""}],
 "evidence": ["근거가 된 짧은 인용(정확히)"]}
```

## 일꾼 지시문
일꾼은 서로 독립된 에이전트여야 한다. 특히 대화를 보지 않고 답하는 일꾼은 문항을 만든 일꾼과 달라야 하고, 프로젝트 지시 파일이 자동으로 읽히지 않는 폴더에서 돌려야 한다(예: 저장소의 작업 규칙 문서가 맥락으로 들어가면 그 저장소 문항이 맥락 없이 풀린다). 모든 일꾼에게 "정해진 파일만 읽고 정해진 파일에만 쓴다"를 지시한다.

### 1. 문항 작성
> 사람이 AI의 제안을 승인한 뒤 자기 프로젝트의 상태를 정확히 알고 있는지 확인하는 서술형 문항을 만든다. 일반 지식이 아니라 이 프로젝트에서 정해진 결과로 생긴 환경을 묻는다. 입력: 패킷 파일(pid 범위 지정). 패킷마다 승인이 실제로 결정의 승인인지 먼저 보고, 아니면 건너뛴다. 위 "문항 규칙"과 "문항 형식"을 지킨다. 문항마다 `common_wrong`을 정직하게 쓰고, 맥락을 모르는 유능한 사람이 맞힐 것 같으면 고치거나 버린다. 근거 인용은 패킷에 그대로 있는 문장이어야 한다.

### 2. 정답 기준을 지금 기준으로 확인
> 문항마다 원래 세션 이후의 변화를 찾는다. 같은 프로젝트의 이후 세션을 핵심어로 찾고, 저장소는 읽기만 한다(git log/show/ls-files/grep, 파일 읽기만 허용. 수정, 설치, 빌드, 서버 실행, 체크아웃 금지). 코드와 설정이 대화보다 우선하고, 나중 것이 먼저 것보다 우선한다. `then_state`, `later_changes`, `now_state`를 채우고, 바뀌었으면 `key_points`를 지금 기준으로 고친다. 지금 상태를 확인할 수 없으면 그렇게 적는다.

### 3. 대화를 읽고 답하기
> 패킷과 `later_changes`만 읽고, 질문마다 한두 문장으로 답한다. 정답 기준 파일은 열지 않는다.

### 4. 대화 없이 답하기
> 질문 파일만 읽는다. 다른 파일은 열지 않는다. 질문 글과 상식만으로 구체적인 답을 쓴다. "모르겠음"은 쓰지 않는다.

### 5. 채점 (출처를 가림)
> 질문, 정답 기준, 답안 X와 Y만 본다. 누가 썼는지 모른다. 핵심 사실이 실질적으로 있으면 맞음, 부분 조건이면 부분, 아니면 틀림. 어느 프로젝트에나 맞을 일반적인 답은 틀림. 핵심 사실과 모순되는 주장을 덧붙였으면 최대 부분. 이유를 한 줄로 쓴다.

### 6. 사용자 답 채점과 사실 확인
> 사용자 답을 5번과 같은 규칙으로 채점한다. 틀림, 부분, 확신 오답으로 나온 답은 모두 2번처럼 이후 세션과 저장소를 다시 확인해 답을 주장 단위로 사실 확인한다. 사용자가 정답 기준보다 최신 상태를 알고 있으면 바로잡는다. 결과는 "지금 사실과 맞음 / 그때 기준으로만 맞음 / 부분 / 틀림 / 확인 불가" 중 하나와 근거(세션, 커밋, 파일 위치)다. 원래 채점은 지우지 않고 따로 남긴다. 사용자가 알고 있는 것과 지금 동작이 다르다고 확인되면 "생각과 실제가 다른 곳"으로 따로 적는다. 사용자에게 채점을 확인받지 않는다.
